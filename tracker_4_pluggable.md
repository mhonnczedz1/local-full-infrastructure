## 1. Spec summary

### Goal
Adding a service is a subscription file plus a team-owned config repository. Teams write only to their own repos and never to the central GitOps repo. The platform controls what exists (subscriptions, ApplicationSets, the `teams` project, add-ons, Terraform, the deny list). Teams control how their service runs in each environment, including prod protection.

### The four kinds of repository

| Repo | Holds | Written by |
|------|-------|------------|
| `lfi-infrastructure-gitops` | `platform/registry.yaml`, `platform/subscriptions/<cluster>/<service>.yaml`, `platform/overrides/`, generated ApplicationSets and the `teams` AppProject, add-ons, Terraform, scripts, the deny list | Platform |
| `lfi-service-templates` (new) | Components `replicas-1`, `canary-manual-gate`, `storage-gp3`, referenced by URL and pinned by tag; scaffolds `web-service` and `db-service`, copied once | Platform, plus team PRs |
| `lfi-service-1-config`, `lfi-service-2-config` (new) | `<cluster>/<env>/env.yaml`, `<cluster>/<env>/app/kustomization.yaml`, `base/`, optional `postgres/` | Each team and its CI |
| `lfi-service-1-app`, `lfi-service-2-app` | Code and CI | Each team |

### Decisions (full text and reasons are in the guide)

1. Template, not fork: refactor in place, tag `guide-3-complete`, mark the repo as a GitHub template.
2. Discovery: a matrix of two Git generators per cluster. Subscriptions say what exists; each config repo says which environments it has (an `env.yaml` per environment directory).
3. Platform adjustments: a merge generator lays an optional `platform/overrides/<cluster>/<service>.yaml` on top of a subscription (for example a `targetRevision` pin).
4. Environments are chosen by each team. Terraform still creates the namespaces from its `environments` variable.
5. Prod protection is a team concern. Nothing prod-specific in the GitOps repo.
6. Shared behavior lives in components named for what they do, in the templates repo, pinned by tag.
7. Scaffolds are copied once, not referenced.
8. Datastores get a second ApplicationSet: no prune, no cascading delete, `preserveResourcesOnDeletion`.
9. CI writes `images[0].newTag` in the service's own config repo, migrated in two steps (dual write, then single write).
10. Application names and namespaces are unchanged for existing services, so the new Applications adopt what runs.
11. One AppProject, `teams`: only `<project>-*-config` repos, only `<prefix>-*` namespaces, nothing cluster-wide.
12. The registry holds project identity and clusters. Services are subscriptions. ApplicationSets and the project are generated by `scripts/gen-appsets.sh` and checked for drift by `scripts/check-contract.sh`.
13. Add-ons, the Makefile registry reads, Terraform state keys and prefix delegation are unchanged from the first draft.
14. Stamping is a script plus a checklist for the other repos.

### Cutover order (Phase 20.3)
CI dual write, then Move 1 (ship subscriptions, no cluster effect), Move 2 (drop finalizers), Move 3 (delete the six Application files), Move 4 (ApplicationSets and project), then CI single write. The old `kubernetes/` tree is retired only after the commands follow the config repos (Task 20.4.5). Releases are frozen from Task 20.1.2 until Task 20.4.2.

## 2. Risks

| # | Risk | Where it is handled |
|---|------|---------------------|
| R1 | A merge generator nested in a matrix, `pathParamPrefix`, a templated `revision` and the `get ... \| default` template calls cannot be checked without a running ArgoCD | Task 20.2.3 spike on a throwaway ApplicationSet. Fallback A in Appendix I: `useMerge: false` |
| R2 | Remote Kustomize components need the repo server to reach the templates repo, and the repo must be public | Task 20.1.3 fetches them as ArgoCD will; spike part 1 shows `Unknown` if they cannot be fetched |
| R3 | A team repo is trusted by ArgoCD | The `teams` AppProject (Task 20.2.2) |
| R4 | CI needs a credential that can write to the config repos | Task 20.3.2 widens the existing `GITOPS_PAT`; Appendix I covers the 404 |
| R5 | `release.sh` and `rollback.sh` assumed one repo and one history | Tasks 20.4.2 and 20.4.3 rewrite them for per-service config repos. Rollback cannot see builds from before the move |
| R6 | Seeding config repos with wrong tags would change images at cutover | Seeded from live tags; `parity.sh` compares at 20.1.3, 20.3.1 and 20.3.6 |
| R7 | One unreachable config repo freezes the services ApplicationSet | Spike part 3 measures it; `scripts/check-contract.sh --online` guards it; Appendix I, fallback B |
